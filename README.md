# Supply Chain Trust Layer

**Trust contracts for supply-chain decisions.**

Supply-chain decisions depend on data spread across ERP, warehouse and supplier systems. Those systems often disagree, and a normal AI copilot will answer from whichever system it queries, producing confident but wrong answers.

This project adds a **governed trust layer** on top of existing systems. Before any order decision or AI answer is shown, the data behind it is checked against a versioned **trust contract**. If the sources disagree, are stale, or there is not enough evidence, the decision is blocked as `REVIEW_REQUIRED`, and the exact source records are shown as evidence.

> Most copilots answer questions. This one checks whether an answer is safe to trust.

Everything runs inside Snowflake: data, trust engine, semantic layer, AI agent and UI.

---

## Architecture

```text
Source systems (ERP, Warehouse, Supplier portal)  -- simulated
                     |
RAW       Immutable source records (what each system reported)
                     |
CORE      Canonical entities, ID mappings, inventory claims, orders
                     |
TRUST     Business definitions, trust contracts,
          evaluations and record-level evidence
                     |
APP       Views + order decision (REVIEW_REQUIRED / CAN_FULFILL /
          INSUFFICIENT_STOCK)
                     |
SEMANTIC  Snowflake Semantic View (governed business meaning)
                     |
AGENT     Cortex Agent: semantic view + governed decision tool
                     |
UI        Streamlit in Snowflake dashboard
```

### Trust statuses

| Status | Meaning |
|---|---|
| `VERIFIED` | Sources agree within the allowed variance and are fresh |
| `CONFLICTED` | Sources disagree beyond the allowed variance |
| `STALE` | At least one source is older than the allowed age |
| `INSUFFICIENT_EVIDENCE` | Fewer sources than the contract requires |

**Core rule:** if inventory is not `VERIFIED`, the order decision is `REVIEW_REQUIRED`, never a guess. When verified, the system uses the **lowest** reported quantity so it never overstates stock.

## Demo

After a clean build, the dashboard shows four orders, each hitting a different trust path:

| Order | Part | Trust status | Decision |
|---|---|---|---|
| ORD_001 | Battery Cell (ERP 500 vs WMS 120) | `CONFLICTED` | `REVIEW_REQUIRED` |
| ORD_002 | Drive Motor (ERP 300 vs WMS 298) | `VERIFIED` (298) | `CAN_FULFILL` |
| ORD_003 | Controller Board (ERP only) | `INSUFFICIENT_EVIDENCE` | `REVIEW_REQUIRED` |
| ORD_004 | Cooling Fan (data 3 hours old) | `STALE` | `REVIEW_REQUIRED` |

**Live flow:**

1. Show ORD_001 in the dashboard: red **REVIEW REQUIRED** with ERP 500 vs WMS 120 evidence.
2. Ask the agent (**AI & ML > Agents > SUPPLY_TRUST_AGENT**): *"Can we fulfill order ORD_001?"* It refuses to confirm and cites the evidence.
3. Run `scripts/demo_recount.sql` (ERP corrected to 125, WMS confirms 120).
4. Refresh the dashboard: amber **INSUFFICIENT STOCK, verified 120 vs required 150**.
5. Ask the agent again: it now gives the verified answer.
6. Open the audit trail: both evaluations are kept, each linked to its source records.

A normal chatbot trusting ERP would have said "500 available, fulfill the order".

## Scripts

| File | Purpose | Rerun safe? |
|---|---|---|
| `scripts/demo_recount.sql` | Demo step: recount resolves the ORD_001 conflict | **No, once per clean build** |
| `scripts/reset_database.sql` | Drops `SUPPLY_TRUST_DB` for a clean rebuild (warehouse kept) | Yes, but destructive |

After `demo_recount.sql`, `verify_setup.sql` will show FAIL by design, because the data has moved to the resolved state.

**Clean restart:** run `scripts/reset_database.sql`, then repeat the build order.

## Verification

`sql/tests/verify_setup.sql` checks:

- Row counts (data loaded exactly once)
- Referential integrity (Snowflake does not enforce PRIMARY KEY / FOREIGN KEY on standard tables)
- Business logic: 76% variance detected, ORD_001 is `CONFLICTED` and `REVIEW_REQUIRED`
